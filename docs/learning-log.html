DeepSeek Harness anatomy, as seen from a plugin

DSH is a Cordis application: everything is a plugin that provides or injects services. A community plugin is an npm package that Cordis loads by name.

The plugin shape

// src/index.ts — the whole contract Cordis needs
export const name = 'signal-integrity'          // row id in the composed config
export const inject = ['tools', 'subprocess']   // services this plugin needs before apply() runs
export const Config = Schema.object({ ... })    // Schemastery: validated + defaulted at load
export function apply(ctx: Context, config: Config) {
  const worker = new WorkerClient(ctx, config)
  registerReadyTool(ctx, worker, config)        // ctx.tools.register(defineTool({...}))
  registerInspectTool(ctx, worker, config)
}
Why Schemastery, not zod? Cordis validates Config through the Standard Schema interface at load time. A zod object fails that check and the plugin never mounts. The docs say it; the code confirms it.

How a plugin reaches the model

flowchart LR P[npm package
dsh-signal-integrity] -->|dsh plugin add| PR[Profile
~/.dsh/profiles/web] PR -->|dsh.profile.bundles| L[Loader composes layers] B[dsh-base patch] --> L W[dsh-web-app patch] --> L C[cordis.patch.yml
insert: signal-integrity] --> L L -->|import lib/index.js| A[apply ctx config] A -->|ctx.tools.register| R[Tool registry] R -->|JSON schema| M[Model sees si_ready, si_inspect]

Layer order: each bundle's patch in list order → the profile's cordis.patch.yml → $DSH_HOME/cordis.patch.yml → --patch overlays. A patch replaces a row's whole config, never deep-merges.

The model sees only what is in the built lib/index.js. Editing src/ does nothing until pnpm build and a profile restart. This bit us once: the model saw si_ready only, then read the plugin source and drove the worker by hand.

Milestone 1 · scaffold (PR #1, merged)

  • Installable bundle; dsh plugin --profile web add ../dsh-signal-integrity writes a link: dependency and the bundle row.
  • si_ready spawns uv run --project <plugin>/python --frozen --no-dev python -m dsh_si and reports interpreter and package versions. A broken environment is a result with a remedy, not an exception.
  • Cancellation: exec.signal → spawn({signal, graceMs}) → SIGTERM then SIGKILL on the process tree; the test asserts no survivor via pgrep.
  • Tests never need a model or key: a bare Context + SystemPrompt + ToolRuntime + LocalSubprocessRuntime, then ctx.tools.execute(...).

Milestone 2 · inspection (PR #2, open)

  • si_inspect(path): sha256, header metadata (ports, span, unit, format, reference impedance, version, comments, mixed-mode hint), quality block, warnings, questions, required_by_device.
  • Quality: IEEE P370 PQMi/RQMi/CQMi with bands from scikit-rf, plus exact worst-point passivity and reciprocity.
  • Rejections with structured codes: relative path, missing file, wrong suffix, malformed data, non-monotonic frequency, NaN.
  • Synthetic examples: lossy line, series RL, uncoupled 4-port, anti-causal, active, non-reciprocal.

Milestone 3 · lumped extraction (branch open)

  • python/dsh_si/lumped.py: five documented functions raising NotImplementedError; tests/test_lumped.py holds analytic RL, floating-element, capacitor, and RLC-resonance checks as xfail(strict=True, raises=NotImplementedError).
  • Coming from the agent side: si_analyze skeleton, report.py (Matplotlib PNGs, HTML, CSV, results JSON), inline image return, an |S| overview plot for si_inspect.

How it works, end to end

One conversation, three hops: the model, the TypeScript tool, the Python worker.

sequenceDiagram participant U as Engineer participant M as Model (DeepSeek-V4-Flash) participant I as si_inspect (TS) participant W as dsh_si worker (Python) participant Q as ask_user_question U->>M: "Inspect lossy_line_20mm.s2p" M->>I: si_inspect{path} I->>W: {"protocol":1,"command":"inspect","payload":{path,tolerances},"limits":{max_memory_mb}} W->>W: sha256 · skrf.Network · P370 metrics · exact checks · build questions W-->>I: {"ok":true,"result":{hash,metadata,quality,warnings,questions,required_by_device}} I-->>M: rendered text incl. questions JSON + "pass hash to si_analyze" M->>Q: ask_user_question{questions} (array forwarded verbatim) Q-->>U: Device? Port roles? U-->>Q: transmission_line / through Q-->>M: answers M->>M: si_analyze{path, hash, interpretation} (milestone 3)

The wire protocol (mirrored, tested)

request  = { protocol: 1, command: 'ready'|'inspect'|'analyze', payload: {...}, limits: { max_memory_mb? } }
response = { protocol: 1, ok: true,  result: {...} }
         | { protocol: 1, ok: false, error: { code, message, detail? } }
codes    = bad_request | unsupported_command | file_not_found | parse_error | unsupported_format
         | interpretation_invalid | hash_mismatch | numerical_error | report_write_failed | internal

tests/protocol-mirror.spec.ts spawns the worker and asserts the Python constants equal the TypeScript ones, so drift fails CI instead of failing at a user's desk.

Error routing

WorkerClient.call
  spawn fails / ENOENT ........ WorkerError('spawn_failed')  → si_ready: "uv not found: install uv or set pythonCommand"
  signal aborted .............. WorkerError('cancelled')     → rethrown; tool result isError
  no stdout, non-zero exit .... WorkerError('crashed')       → "worker produced no response (exit code 3)" + stderr tail
  stdout not JSON / wrong ver . WorkerError('protocol')
  ok:false .................... WorkerError(code from worker)

si_inspect.execute
  code ∈ {bad_request, file_not_found, parse_error, unsupported_format} → throw Error(message)   (about the file)
  any other WorkerError (not cancelled) → throw Error("worker failed (code) … Call si_ready")   (about the environment)

Why this way

Each decision, the alternative it beat, and the evidence.

Quality checks and the first real data

What each metric means, what its number is, and what three real measurements say.

Two layers per check

CheckIEEE P370 metric (0–100 %, bands)Exact detail
PassivityPQMi: share of frequency points where the 2-norm of S ≤ 1. Bands: >99.9 good · >99 acceptable · >80 inconclusive · else poor.largest singular value of S per point vs 1 + tol; worst point, violating count
ReciprocityRQMi: integrated |Sij − Sji| difference.max |Sij − Sji| per point vs tol; worst point, violating count
CausalityCQMi: share of consecutive-frequency S vectors rotating clockwise in the complex plane. Screening only; sensitive to sampling.none (no exact per-point form on sampled data)
One-ports: scikit-rf's P370 metrics need off-diagonal terms and raise; the exact passivity check still runs.

Lessons and gotchas

Things that cost time today, recorded so they cost nothing tomorrow.

  1. Rebuild before you demo. The linked profile loads lib/index.js. After a TypeScript change: pnpm build, restart dsh web. Otherwise the model sees stale tools and improvises.
  2. inotify exhaustion on this host. dsh web crashed with ENOSPC from the live config watcher. The profile now uses patchReload: startup; raising fs.inotify.max_user_instances needs sudo.
  3. pkill -f kills its own shell. The pattern matched the bash command line that contained it. Use a bracketed character class: pkill -f 'bin\.ts web --port 309[9]'.
  4. Never paste the browser-trust URL. It authorizes a browser to the local server. Local-only and rotating, but a secret nonetheless.
  5. Shell cd persists across tool calls. A cd python && … chain silently skipped its edits once because the shell was already in python/. Use absolute paths.
  6. Published packages lag the checkout. npm has 0.1.2-rc.1, the dev runtime is 0.1.3-alpha.1. Peer ranges are >=0.1.2-rc.1 <0.2.0; tests run against the published versions.
  7. The model will go around a missing tool. Given only si_ready, DeepSeek read the worker source and called it through bash. Impressive, and a reminder that tool availability, not instructions, defines the workflow.
  8. scikit-rf P370 refuses one-ports. Every metric, not just reciprocity. Report "not applicable" and keep the exact passivity check.
  9. Real files break assumptions. A 4-port with |Sij−Sji| = 0.45 everywhere is a data-provenance question, not a physics result. The screen exists for exactly this.

Glossary

TermMeaning here
CordisThe plugin/service framework DSH is built on. A plugin exports name, inject, apply, optionally Config.
Context (ctx)The handle a plugin receives; services hang off it (ctx.tools, ctx.subprocess, ctx.attachments, ctx.logger).
ProfileA named DSH installation under ~/.dsh/profiles/<name> with its bundle list and patch file.
BundleAn npm package declaring dsh.bundle.patch; its patch inserts rows into the composed config.
Patch layerYAML list of inserts/overrides applied in order; an override replaces a row's whole config.
ToolA defineTool definition the model can call; validated args in, canonical value out, rendered to content blocks.
Canonical valueThe JSON the tool returns; validated against output.schema, persisted, then rendered.
WorkerThe Python process (python -m dsh_si) that does all numerical work; one per tool call.
TouchstoneText S-parameter format (.sNp, .ts); header sets unit, parameter, format, reference impedance.
IEEE P370Standard for fixture de-embedding and S-parameter data quality up to 50 GHz; its frequency-domain quality metrics are implemented in scikit-rf.
PQMi / RQMi / CQMiP370 initial passivity, reciprocity, causality quality metrics (percent).
Mixed-modeDifferential/common-mode representation (Sdd, Sdc, Scd, Scc) obtained from single-ended data via se2gmm after explicit pairing.
SRFSelf-resonant frequency: where Im(Z) of a lumped element changes sign.
uvPython package/project manager; uv run --project … --frozen guarantees the locked environment.
strict xfailpytest marker: the test must fail now; an unexpected pass fails the suite, forcing the marker's removal when the code lands.
